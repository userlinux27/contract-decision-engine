# Architecture (Архитектура)

## System Overview (Обзор системы)

Пользователь загружает PDF через браузер. Сервер извлекает текст, отправляет в LLM, получает найденные факторы, прогоняет через Decision Engine и возвращает результат.

Пользователь → Браузер (index.html) → FastAPI (main.py) → Decision Engine → LLM
↑
catalog.py (правила)


## Key Components (Ключевые компоненты)

### 1. Frontend (static/index.html)
- Один HTML-файл, без фреймворков (намеренно — чтобы не усложнять эксперимент)
- Три состояния экрана: главный → загрузка → результат
- Drag-and-drop загрузка PDF
- Демо-договоры (3 типа) с предзаполненными результатами
- Замер Time to Decision (времени до принятия решения) на стороне клиента
- Отправка обратной связи: «Что сделал дальше?», «Помог ли отчёт?»
- Отслеживание копирования suggested wording (предложенной формулировки)

### 2. API (main.py)
- FastAPI, один файл
- Эндпоинты:
  - `GET /` — главный экран
  - `POST /analyze` — загрузка PDF, возвращает task_id
  - `GET /demo/{type}` — демо-результат для трёх типов договоров
  - `POST /feedback` — приём обратной связи
  - `POST /analytics/copy` — отслеживание копирования формулировок
- Аналитика: запись в CSV, без базы данных
- Временные файлы: сохраняются в `uploads/`, автоочистка

### 3. Decision Engine (engine/)
- `BaseDecisionEngine` — базовый класс, переиспользуемый для любых типов документов
- `ServiceAgreementEngine` — конкретная реализация для договоров оказания услуг
- `catalog.py` — Decision Catalogue (каталог решений), единственный источник правил

**Алгоритм принятия решения:**
1. Принимает список факторов от LLM (findings)
2. Суммирует веса факторов с учётом confidence (уверенности LLM)
3. Определяет категорию: safe_to_sign / sign_after_changes / do_not_sign
4. Проверяет минимальный confidence для категории
5. Проверяет: есть ли для всех критических факторов suggested wording
6. Возвращает решение + топ-3 причины

### 4. LLM Integration (на День 2)
- OpenAI API или Ollama (локально)
- Промпт из `prompts/service_agreement.md`
- Ответ строго по JSON Schema
- Два режима: реальный анализ и демо (предзаполненные данные)

### 5. Documentation (docs/)
- Obsidian-совместимые Markdown-файлы
- Внутренние ссылки между документами
- Можно открыть как отдельный Vault (хранилище) в Obsidian

## Design Decisions (Проектные решения)

### Почему без базы данных?
Сейчас этап проверки спроса. CSV достаточно для 20–100 событий. База данных — преждевременное усложнение. Добавим на этапе платящих пользователей (Месяц 1).

### Почему без авторизации?
Авторизация добавляет трение в onboarding (входе в продукт), не добавляя ценности на этапе валидации. Сначала докажем, что пользователь возвращается — потом сделаем кабинет.

### Почему без оплаты?
Готовность платить проверяем после готовности возвращаться. Если пользователь не вернулся бесплатно — не вернётся и за деньги.

### Почему один сервер?
Эксперимент не требует масштабирования. Hetzner CX22 (~€4/мес) + Nginx + Let's Encrypt.

### Почему один HTML-файл без фреймворка?
Скорость разработки на этапе эксперимента важнее архитектурной красоты. React/Vue появятся, когда продукт докажет право на жизнь.

## Data Flow (Поток данных)

1. Пользователь загружает PDF
   ↓
2. main.py сохраняет файл в uploads/{task_id}.pdf
   ↓
3. Парсер извлекает текст (pymupdf)
   ↓
4. Текст разбивается на секции по заголовкам (Clause, Article)
   ↓
5. Каждая секция отправляется в LLM с промптом
   ↓
6. LLM возвращает JSON с найденными факторами
   ↓
7. Decision Engine принимает решение
   ↓
8. Результат рендерится в HTML и возвращается пользователю
   ↓
9. События пишутся в CSV (data/analytics.csv)

`

## Security (Безопасность — минимально для v0.1)

- Файлы не хранятся дольше 1 часа (автоочистка)
- Rate limiting: 10 загрузок в минуту с IP
- Входные файлы проверяются: только PDF, макс. 10 МБ
- Никакие данные договоров не передаются третьим лицам
- LLM-запросы: по возможности через локальный Ollama, а не облачный API
