# ТЗ: Миграция Contract Decision Engine на новую архитектуру

## 0. ЦЕЛЬ

Необходимо перенести серверную версию Contract Decision Engine на новую архитектуру с разделением:

```text
main.py
    ↓
api/
    ↓
services/
    ↓
engine/
```

При этом существующая серверная LLM-интеграция должна быть сохранена и продолжить работать:

```text
engine/llm_interpreter.py
        ↓
engine/llm_providers.py
        ↓
OpenAI
        ↓
gpt-4o-mini
```

Миграция должна быть **структурной**, а не функциональной.

### Главный принцип

Нельзя в рамках этой задачи:

* менять Decision Engine;
* менять правила принятия решений;
* менять thresholds;
* менять классификацию;
* менять Rule Detector;
* менять LLM prompt/поведение без отдельного согласования;
* заменять OpenAI другим provider;
* удалять существующую LLM-интеграцию;
* переносить на сервер старую архитектуру вместо новой;
* одновременно делать новые продуктовые функции.

---

# 1. ЦЕЛЕВАЯ АРХИТЕКТУРА

Итоговая архитектура должна быть примерно такой:

```text
                    HTTP
                     │
                     ▼
                 main.py
                     │
                     ▼
                    api/
                     │
                     ▼
          analysis_service.py
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
       parser    classifier   rule_detector
          │          │          │
          └──────────┼──────────┘
                     ▼
              decision_engine
                     │
                     ▼
                LLM enrichment
                     │
                     ▼
                  result
```

При этом:

```text
main.py
```

не должен содержать бизнес-логику.

# 2. ОБЯЗАТЕЛЬНОЕ УСЛОВИЕ: СУЩЕСТВУЮЩУЮ LLM НЕ ЛОМАТЬ


```text

```

использует:

```text
gpt-4o-mini
```

### Жёсткий запрет

ЗАПРЕЩЕНО до отдельного согласования:

* удалять `engine/llm_providers.py`;
* удалять `engine/llm_interpreter.py`;
* заменять `OpenAIProvider`;
* заменять OpenAI;
* менять модель;
* удалять `OPENAI_API_KEY`;
* менять `LLM_PROVIDER`;
* переносить LLM в другой framework;
* переписывать LLM orchestration только потому, что "так красивее".

Сначала необходимо провести аудит существующего LLM flow.

Если для совместимости с новой архитектурой потребуется изменение этих файлов — сначала описать изменение и причину.

Не выполнять такое изменение молча.

# 3. РОЛЬ LLM

Decision Engine остаётся единственным Source of Truth.

Поток:

```text
PDF
 ↓
Parser
 ↓
Classifier
 ↓
Rule Detector
 ↓
Decision Engine
 ↓
Findings
 ↓
LLM Interpreter
 ↓
Enriched Findings
```

LLM получает уже определённые системой findings.

LLM может добавить:

```text
llm_reason
llm_impact
llm_suggested_rewrite
llm_confidence
```

LLM НЕ имеет права менять:

```text
decision
outcome
risk
factor detection
engine result
```

То есть:

```text
Decision Engine = decides
LLM = explains/enriches
```

---

# 4. НОВЫЙ HTTP FLOW

Новая серверная API-архитектура должна использовать асинхронную модель task-based processing.

Целевой flow:

```text
POST /api/analyze
        │
        ▼
     task_id
        │
        ▼
   processing
        │
        ▼
 GET /api/analyze/{task_id}
        │
        ├── processing
        ├── completed
        └── failed
```

После завершения:

```text
GET /api/analyze/{task_id}
```

возвращает результат анализа.

Старая модель:

```text
POST /analyze
    ↓
полный анализ
    ↓
HTTP response
```

не должна быть основой новой архитектуры.

Если старый endpoint существует и нужен для backward compatibility, его можно временно сохранить как compatibility layer, но новая архитектура должна использовать `/api/...`.

# 6.2. Responsibility boundaries

## main.py

Только:

```text
FastAPI()
middleware
startup/shutdown
router registration
health/basic application configuration
```

Никакого:

```text
PDF parsing
classification
rule detection
decision logic
LLM orchestration
```

---

## api/

Отвечает за HTTP.

Например:

```text
POST /api/analyze
GET /api/analyze/{task_id}
```

API layer:

* принимает request;
* валидирует input;
* создаёт task;
* вызывает service;
* возвращает HTTP response.

API layer не должен содержать Decision Engine logic.

---

## services/analysis_service.py

Главный orchestration layer.

Примерная ответственность:

```text
analyze_document(...)
```

Он организует:

```text
parser
→ classifier
→ rule_detector
→ decision_engine
→ llm_interpreter
```

Но сам не должен реализовывать правила Decision Engine.

---

## engine/

Pure business logic.

Сюда относятся:

```text
parser
classifier
rule_detector
decision_engine
```

и существующий:

```text
llm_interpreter
llm_providers
```

# 6.4. Task management

Нужно определить, как будут храниться задачи.

Для текущего Alpha допустима простая in-memory структура, если она уже используется локально.

Например:

```text

    task_id: {
        status: "processing",
        result: ...,
        error: ...
```

Но агент обязан оценить последствия:

* restart;
* concurrent requests;
* memory;
* cleanup.

Не внедрять Redis/Celery/PostgreSQL только ради "правильной архитектуры", если это не требуется текущему Alpha.

Цель — минимальная надёжная реализация.

# PHASE 3 — MIGRATION

## 7. СОЗДАТЬ BACKUP / ROLLBACK POINT

# 7.1. Создать service layer

Создать:

```text
services/analysis_service.py
```

Он должен инкапсулировать orchestration.

Логика:

```text
1. Receive document
2. Parse
3. Classify
4. Detect rules
5. Run Decision Engine
6. Run LLM enrichment
7. Build result
8. Return result
```

---

# 7.2. Создать API layer

Создать соответствующие routers.

Новый endpoint:

```text
POST /api/analyze
```

После загрузки файла:

```text
validate
save temporary file
create task_id
start processing
return task_id
```

Response должен позволять клиенту узнать:

```text
task_id
status
```

---

# 7.3. Status endpoint

Создать:

```text
GET /api/analyze/{task_id}
```

Состояния:

```text
processing
completed
failed
```

Для `completed` возвращается результат.

Для `failed`:

```text
status
error
```

Без утечки секретов, API keys и внутренних sensitive details.

---

# 7.4. Background execution

Агент должен использовать простой механизм background execution, совместимый с текущим FastAPI deployment.

Не добавлять тяжёлую инфраструктуру без необходимости.

Важно:

```text
HTTP request
    ↓
task created
    ↓
response immediately
    ↓
background analysis
```

---

# 7.5. Перенести LLM orchestration

Из `main.py` убрать:

```text
interpreter = LLMInterpreter(get_provider())
enriched_findings = interpreter.interpret(findings)
```

и соответствующую orchestration логику.

Перенести её в service layer.

Целевой flow:

```text
analysis_service
    ↓
LLMInterpreter
    ↓
get_provider()
    ↓
OpenAIProvider
    ↓
gpt-4o-mini
```

---

# 7.6. Decision Engine не изменять

В рамках миграции запрещено изменять:

```text
decision criteria
thresholds
factor logic
risk calculation
outcomes
```

Если при миграции обнаружена проблема в Decision Engine:

```text
STOP
```

зафиксировать проблему отдельно.

Не исправлять её автоматически.

---

# 7.7. Classifier не изменять

Текущие категории должны остаться прежними.

Например:

```text
Service Agreement
NDA
Employment Contract
Tenancy Agreement
Unknown
```

Если фактическая версия отличается — использовать фактические значения.

Не расширять classifier.

---

# 7.8. Rule Detector не изменять

Rule Detector должен выдавать те же findings, что и до миграции.

Изменяется только место его вызова.

---

# 7.9. Temporary files

После анализа временный PDF должен удаляться.

Cleanup должен происходить:

```text
success
failure
exception
```

То есть концептуально:

```text
try:
    analyze()
finally:
    cleanup()
```

---

# 7.10. Error handling

Ошибки должны разделяться:

```text
upload error
parse error
classification error
decision engine error
LLM error
unknown error
```

LLM failure не должен автоматически уничтожать уже полученное решение Decision Engine, если текущая бизнес-логика допускает enrichment failure.

Цель:

```text
Decision Engine result survives LLM failure
```

но фактическое поведение сначала сверить с текущей реализацией.

Не менять это поведение без фиксации в плане.

# 13. ПРАВИЛО STOP

Если во время миграции обнаружено:

```text
Decision Engine отличается
LLM не совместим
старый endpoint используется frontend
deployment устроен иначе
есть неизвестная зависимость
есть конфликт модулей
есть regression
```

агент НЕ должен самостоятельно менять архитектурные предположения.

Он должен:

```text
STOP
↓
describe problem
↓
show evidence
↓
propose options
↓
wait for approval
```

# 14. ГЛАВНЫЙ ИТОГ

После миграции система должна выглядеть концептуально так:

```text
                 Browser
                    │
                    ▼
              POST /api/analyze
                    │
                    ▼
                API layer
                    │
                    ▼
             task_id returned
                    │
                    ▼
          Analysis Service
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
       Document           orchestration
       parsing                 │
                               ▼
                         Classifier
                               │
                               ▼
                         Rule Detector
                               │
                               ▼
                       Decision Engine
                               │
                               ▼
                          FINDINGS
                               │
                               ▼
                       LLM Interpreter
                               │
                               ▼
                       OpenAI Provider
                               │
                               ▼
                         gpt-4o-mini
                               │
                               ▼
                       ENRICHED FINDINGS
                               │
                               ▼
                           RESULT
                               │
                               ▼
                  GET /api/analyze/{id}
                               │
                               ▼
                           Browser
```

При этом принцип системы остаётся:

```text
                  DECISION ENGINE
                         │
                         │ decides
                         ▼
                      DECISION
                         ▲
                         │
                         │ explains/enriches
                         │
                         LLM
```

**LLM не принимает решение.**

# 15. ПОРЯДОК ВЫПОЛНЕНИЯ

Строго:

```text
PHASE 1
AUDIT
  ↓
AUDIT REPORT
  ↓
PHASE 2
PLAN
  ↓
MIGRATION PLAN
  ↓
PHASE 3
MIGRATION
  ↓
PHASE 4
TEST
  ↓
TEST REPORT
  ↓
PHASE 5
DEPLOY
  ↓
PRODUCTION SMOKE TEST
  ↓
FINAL REPORT
```

Нельзя перескакивать через этапы.

Особенно:

```text
AUDIT → сразу код
```

недопустимо.

Сначала показать картину сервера и план.

# КОНЕЧНАЯ ЦЕЛЬ

Получить на production не "новую систему", а:

> **ту же работающую систему с тем же Decision Engine и той же LLM, но с правильным разделением API / services / engine и с новой task-based архитектурой анализа.**

Функциональное поведение должно максимально сохраниться.

Изменяется прежде всего:

```text
ARCHITECTURE
ORCHESTRATION
API FLOW
TASK PROCESSING
```

а не:

```text
BUSINESS LOGIC
DECISION LOGIC
LLM ROLE
```
